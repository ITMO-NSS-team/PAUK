## Развилка 1 (главная): где живёт правда и как правка переживает publish

Neo4j — не источник правды, а витрина: `pauk publish graph` льёт в него
prepared-документы из Mongo через `MERGE ... ON MATCH SET n +=
row.properties`. Что это значит для ручной правки:

| Что сделали руками | Что будет при следующем publish |
|---|---|
| Изменили поле, которое пайплайн тоже пишет | Затрётся автоматическим значением |
| Изменили поле, которого нет в prepared-строке | Переживёт |
| Удалили узел | Воскреснет (`MERGE` создаст заново) |
| Удалили связь | Пересоздастся |
| Создали узел с собственным id | Переживёт (пайплайн его не знает) |
| Слили два узла руками | Дубль воскреснет, если `merged_ids` не записан |

Плюс `pauk dedup graph` может схлопнуть узел независимо от publish.

### Вариант A — править только Neo4j, ничего не защищать

Кнопка «сохранить» дёргает `upsert_nodes_batch` и всё.

- **+** Ноль инфраструктуры, день работы.
- **−** Правка живёт до следующего прогона. Для «поправить ФИО перед
  демо» годится, как основа админки — нет.
- **−** Расхождение Neo4j и Mongo нигде не зафиксировано: через месяц
  никто не знает, какие числа настоящие.

Отвергнут вводной №4.

### Вариант B — править prepared-слой в Mongo и перепубликовывать

Правка идёт в `publications`/`persons`/... в Mongo, потом `pauk publish
graph --group <...>`.

- **+** Источник правды один. `_version`/`revisions` уже ведут историю.
- **+** Правка видна и следующим стадиям обогащения, не только в графе.
- **−** Не спасает сама по себе: следующий `pauk enrich` перезапишет
  поле из внешнего API. Нужна пометка «поле ручное» — то есть тот же
  слой оверрайдов, только этажом ниже.
- **−** Долго: чтобы увидеть правку в графе, надо перепубликовать группу
  (а сущность может принадлежать нескольким группам).
- **−** Не покрывает то, чего в prepared нет вовсе: `LinkCandidate`,
  рёбра `MENTIONS_LINK`, результаты граф-дедупа.

Как единственный механизм — не годится. Как часть гибрида — нужен
(см. этап 4).

### ~~Вариант C — слой ручных оверрайдов поверх графа (рекомендуется)~~ — СДЕЛАНО

Реализован в `pauk/graph/overrides.py`. Отличия от плана ниже — в конце
раздела.

Отдельная коллекция в Mongo — журнал ручных решений, который
переприменяется после каждой публикации.

```
graph_overrides:
{
  _id:        "<kind>:<target>",        # детерминированный, чтобы правка была идемпотентной
  kind:       "node" | "rel",
  label:      "Person",                 # или rel_type + src/tgt для связи
  target_id:  "A5023888391",
  op:         "set" | "unset" | "delete" | "create",
  fields:     {"name_ru": "Иванов И. И."},
  auto_value: {"name_ru": "Ivanov I."},  # что было до правки — для отчёта о конфликте
  actor:      "user:petrov",
  note:       "сверено с приказом от 12.03",
  active:     true,
  created_at, updated_at
}
```

Применение — одна идемпотентная функция `apply_overrides(client,
mongo_db)`, вызываемая из трёх мест:

1. сразу при сохранении правки в панели (мгновенный эффект);
2. в конце `load_prepared_rows` — **после** промоушена кандидатов и
   всех фолдов, последним шагом (у `load_jsonl_group` уже есть на руках
   и `mongo_db`, и клиент — новых зависимостей не появляется);
3. в конце `run_graph_dedup`;
4. отдельной командой `pauk overrides apply` — на случай ручного
   вмешательства в базу.

Дополнительно: `op: "delete"` работает не только как удаление, но и как
**tombstone** — `jsonl_loader` должен отфильтровать эти id до загрузки,
иначе узел будет пересоздаваться и удаляться каждый прогон, засоряя
аудит.

- **+** Правка переживает всё: publish, дедуп, повторный enrich.
- **+** Видно, что именно правилось руками, — это отдельный, читаемый
  список, а не растворённые в графе значения.
- **+** `auto_value` даёт бесплатный отчёт о конфликтах: «источник
  теперь говорит X, ваш оверрайд всё ещё Y» — отдельный экран в панели.
- **+** Откат правки = снять `active`, применить заново.
- **−** Ещё одно место, которое надо не забыть переприменить: правка,
  сделанная в обход слоя (Neo4j Browser, руками), останется незаметной.
- **−** Двойная запись: правка попадает в граф дважды (при сохранении и
  при следующем publish). Идемпотентность обязательна, иначе аудит
  засоряется пустыми «изменениями».

**Сделано, с отличиями от плана:**

1. **`fields` мержатся, а не заменяются.** В схеме выше один документ на
   узел, и это правильно, но при второй правке другого поля того же узла
   документ нельзя перезаписывать целиком — иначе первая правка молча
   исчезнет. `auto_value` при этом пишется только для полей, которых в
   документе ещё не было: иначе вторая правка затрёт исходное
   автоматическое значение, и экран конфликтов будет сравнивать правку с
   правкой.
2. **Вызов из `load_prepared_rows` невозможен** — у этой функции нет
   `mongo_db` (в плане сказано обратное). Вызов сделан из
   `load_jsonl_group`, сразу после неё: та же точка по смыслу, но с базой
   на руках.
3. **Реализованы только `set` и `delete`.** `create` покрывается
   `pauk admin node create` (узел с собственным id пайплайн и так не
   трогает), `unset` — это `set` в `null`. Плодить операции, у которых нет
   своего поведения, смысла нет.
4. **Надгробия фильтруются в `load.py::_drop_tombstoned`**, а не в
   `jsonl_loader` — там, где строки ещё лежат по именам сущностей и
   известна метка каждой.
5. **Идемпотентность проверяется сверкой значения** с тем, что уже в
   графе: запись не делается, если сходится. Под тестом отдельно —
   повторное применение не должно давать ни одной записи аудита.
6. **Связи — только удаление.** `kind: "rel"`, `op: "delete"`: добавленное
   руками ребро публикацию переживает само (загрузчик рёбра создаёт, но не
   удаляет незнакомые), а удалённое пересоздаётся `MERGE` — его и надо
   помнить. `load_prepared_rows` принимает набор таких пятёрок
   `(метка источника, тип, метка цели, id источника, id цели)` и
   выбрасывает их до загрузки. Команды: `pauk admin rel delete` (запоминает,
   `--once` — нет) и `pauk admin overrides undo-rel` (вернуть связь).

### Вариант C' — оверрайды прямо в графе

То же самое, но список ручных полей хранится свойством самого узла
(`manual_fields: ["name_ru"]` + значения JSON-текстом), а `client.py`
после `SET n += row.properties` накладывает их обратно.

- **+** Одно место (клиент), ничего не надо переприменять снаружи.
- **−** Значения придётся хранить JSON-текстом: Neo4j не хранит вложенные
  map-свойства (правило репозитория). Разбор — на стороне Python, то
  есть тот же дополнительный проход, только менее явный.
- **−** Узлы засоряются служебными полями, которые потом полезут в
  `cache export` и `generate_data`.
- **−** История правок теряется — только текущее значение.

Хуже C по всем пунктам, кроме одного, и этот один (не надо
переприменять) обесценивается тем, что Mongo и так открыта в момент
publish.

### Вариант D — event sourcing: граф целиком выводится из журнала

Все изменения (и пайплайновые, и ручные) — события; граф
пересобирается их проигрыванием.

- **+** Идеальная история и откат в любую точку.
- **−** Переписывание всего слоя загрузки. Для объёмов проекта — резко
  избыточно.

Не рекомендуется.

**Рекомендация по развилке 1: C** (оверрайды в Mongo + переприменение),

## ~~Развилка 2: слой мутаций — где живёт логика CRUD~~ — СДЕЛАНО

Реализован в `pauk/graph/mutations.py`, ровно как описано ниже. Одно
отличие и одна находка — в конце раздела.

Независимо от того, что будет фронтендом, писать в Neo4j «из
обработчика HTTP-запроса» нельзя. Нужен доменный модуль, например
`pauk/graph/mutations.py`, который умеет:

- `create_node(label, props)` / `update_node(label, id, patch)` /
  `delete_node(label, id, cascade: bool)`;
- `create_rel(...)` / `update_rel(...)` / `delete_rel(...)`;
- `merge_nodes(label, dup_id, canonical_id)` — поверх существующего
  `merge_*_nodes_batch`, но **обязательно** дописывая `merged_ids` на
  канонический узел, иначе `fetch_merged_id_map` не удержит дубль от
  воскрешения;
- валидацию: метка/тип связи — **только** из закрытого перечня
  `NODE_REGISTRY` и словаря связей; поля — только из `prop_fields`; типы
  — из pydantic-моделей `pauk/models/`.

Валидация меток не косметическая: `client.py` интерполирует метки и типы
связей прямо в текст Cypher (`f"MERGE (n:{label_str} ...)"`) — параметром
их передать нельзя, это идентификаторы. Пока единственный источник этих
строк — наши собственные литералы, всё в порядке; в момент, когда
источником станет HTTP-запрос, отсутствие белого списка превращается в
инъекцию. Это то место, где ошибиться дороже всего.

Там же — оптимистичная блокировка: клиент присылает `updated_at`,
который видел, запись отклоняется при расхождении. Без неё два
редактора молча затирают друг друга, и в аудите это выглядит как две
законные правки.

Плюс подхода: тот же модуль обслуживает и CLI (`pauk admin ...`), и
HTTP-роуты, и будущие скрипты. Всё, что снаружи, — только парсинг
аргументов и `actor_context`.

**Сделано, с уточнениями:**

- **Блокировка работает на `updated_at` узла.** Поля нет в pydantic-моделях,
  но узлы графа его несут: `client.py::upsert_node_batch` пишет
  `n.updated_at = datetime()` в обеих ветках `MERGE`. Подделать версию
  обычной правкой нельзя — `props_clean` не пропускает
  `id`/`created_at`/`updated_at` снаружи.
- **Типы пока проверяются не по pydantic.** `--set` читает значение как
  JSON (`stars_num=10` → число, `has_readme=true` → булево), иначе как
  строку. Полная проверка требует карты «метка → модель», которой нет:
  в графе `Person` — одна метка, а в модели 35 полей, часть из них в граф
  не публикуется. Логичное место для этого — этап 2, где формы панели всё
  равно должны знать тип каждого поля.
- **Найдено при живом запуске:** `created_at` публикуется загрузчиком для
  `Person`, то есть попадал в список редактируемых полей, — но принадлежит
  базе, и любая запись его отвергала. `pauk admin schema` обещал поле,
  которого нельзя коснуться. Исключён из белого списка вместе с `id` и
  `updated_at`.

## Развилка 3: транспорт и фронтенд

| Вариант | Плюсы | Минусы |
|---|---|---|
| Neo4j Browser + сниппеты Cypher | Ноль кода | Нет аудита актора, нет валидации, никакой защиты от опечатки в `MATCH`; недоступно нетехническому пользователю |
| CLI `pauk admin ...` | Дёшево, скриптуется, `actor_context` бесплатно | Не панель; но это идеальный первый потребитель слоя мутаций |
| Write-роуты в `pauk/gui/serve.py` | Ноль новых зависимостей | Аутентификацию, CSRF, парсинг тела, валидацию — руками на `SimpleHTTPRequestHandler`. И смешивает публичную карту с записью в БД |
| **Отдельный сервис FastAPI (`pauk/admin/`)** | Валидация pydantic-моделями (они уже есть), автодоки, нормальные зависимости для auth | +2 зависимости (`fastapi`, `uvicorn`) |
| Готовая админка (Retool и подобные) | Быстрый старт | Внешний сервис поверх лабораторных данных с ПД — нет |

**Выбрано (вводная №3): FastAPI отдельным сервисом.** Важное следствие:
`pauk/gui/serve.py` остаётся read-only раздачей статики. Карту можно
оставить открытой, админку — закрыть; на публичном порту физически нет
маршрутов записи.

Фронтенд самой панели — отдельная развилка:

- **Jinja2 + HTMX, сервер-рендер (рекомендуется).** CRUD-формы — ровно
  тот случай, где сервер-рендер выигрывает. Нет сборки, нет бандлера —
  как и у существующего `web/`.
- **SPA на React/Vue.** Требует бандлера, которого в репозитории
  сознательно нет.
- **Вкладка в существующей статике `web/`.** Смешивает публичную карту с
  админкой — ровно то, чего мы избегаем разделением сервисов.

Полезная дешёвая деталь: ссылка «редактировать» из карточки узла на
карте в панель (`/admin/node/Person/A5023888391`).

## Развилка 4: аутентификация

При вводной «несколько человек, простой логин»:

- **HTTP Basic за nginx** — минимум кода, но актор в аудите — только имя
  из `.htpasswd`, и разлогиниться нельзя.
- **Cookie-сессия, пользователи в Mongo (рекомендуется)** — коллекция
  `admin_users` (`login`, `password_hash`, `role`, `active`), хеш через
  `hashlib.scrypt` из stdlib (без `passlib`/`bcrypt` в зависимостях).
  Даёт настоящий `actor_context(f"user:{login}", source="admin-ui")` и
  задел под роли из вводной №1.
- **OAuth (ITMO ID / GitHub)** — правильно в перспективе, но требует
  регистрации приложения и внешнего доступа; сейчас преждевременно.

Отдельно: панель показывает ФИО и почты живых людей
(`data/static/russian_names.csv` — персональные данные, не коммитятся):
доступ к ней — сам по себе доступ к ПД, и это аргумент за настоящий
логин, а не общий пароль. При выходе панели за пределы VPN нужен TLS.

**Уточнение по инфраструктуре** (заменяет прежнее утверждение, что Neo4j
работает без аутентификации, — оно неверно): пароль на Neo4j задан, и
`Neo4jClient` вообще отказывается стартовать с пустым
(`ValueError: Neo4j password is empty`).

~~Остаётся открытым вопрос про отдельного пользователя для панели.~~
**Решено:** пользователь один, разделение прав — на уровне
приложения, **но Neo4j не выставляется наружу**.

Что из этого следует для реализации:

1. **Панель — единственный путь к записи в граф.** Раз к базе нельзя
   подключиться снаружи, весь риск сосредоточен в панели, и защита
   целиком на слое мутаций: закрытый перечень меток, типов связей и
   полей, произвольный Cypher невозможен. Это уже сделано (развилка 2),
   но теперь это единственная блокировка — значит
   роуты панели обязаны ходить только через `pauk/graph/mutations.py`,
   без прямых вызовов `Neo4jClient`.
2. **Разворачивать панель рядом с базой.** Neo4j слушает только внутри
   периметра, наружу открыт лишь порт панели. Отдельная сеть в
   docker-compose или firewall — вопрос к тем, кто настраивает сервер.
3. **Логин обязателен** Панель показывает ФИО и почты
   живых людей, и она же — единственный вход в базу.

## Развилка 5: аудит — куда писать и как показывать

`JSONLAuditSink` работает, но для ленты изменений в UI (фильтры по
актору/сущности, пагинация, поиск) файл не годится.

- **`MongoAuditSink`** — коллекция `audit`, индексы по
  `(entity_type, entity_id, timestamp)` и `actor`. В
  `docs/architecture/neo4j-graph.md` это уже помечено как
  «рассматривается». Реализуется за час: `AuditSink` — узкий протокол,
  ничего вне модуля не меняется.
- **`Neo4jAuditSink`** (`:AuditEvent`-узлы в той же транзакции) —
  единственный способ закрыть известный разрыв «аудит пишется после
  коммита»; но узлы аудита в графе будут мешать `cache export` и
  `generate_data`, придётся везде их исключать.

~~**Рекомендация:** `MongoAuditSink` рядом с JSONL (не вместо — JSONL
удобно грепать), Neo4j-синк не делать.~~

**Сделано.** `MongoAuditSink` и `MultiAuditSink` (пишет в оба синка
подряд), собираются фабрикой `build_audit_sink(config, db)`; открывать
граф всюду, где он меняется, следует через `audited_client(config, db)`.
Neo4j-синк не делали, как и рекомендовано.

Нюансы, которых не было в плане:

- **Значения, которые BSON не принимает** (драйвер отдаёт свои типы вроде
  `neo4j.time.DateTime`), сохраняются текстом. Аудит не должен быть тем,
  что уронит запись, — та же причина, по которой в JSONL-синке стоит
  `default=str`.
- **Синк, который упал, не проглатывается** `MultiAuditSink`: потерять
  запись аудита молча хуже, чем громко упасть.
- **Индексы** `(entity_type, entity_id, timestamp)` и `(actor, timestamp)`
  добавлены в `ensure_indexes`, туда же — индекс для `graph_overrides`.

**Откат.** Для правок из панели он честно строится обратным дифом: батч
из одной строки, полный `diff: {поле: (было, стало)}`. Ограничение,
которое надо назвать вслух: **откатить слияние узлов нельзя**.
`_fold_nodes_batch` делает `DETACH DELETE` дубля, а аудит диффит только
свойства узлов — связи в дифе не отражены сознательно. Чтобы ручной
merge стал обратимым, нужно перед фолдом сохранять полный снимок дубля
вместе с его связями (в те же оверрайды или в `revisions`). Пока это не
сделано, ручное слияние в UI должно спрашивать подтверждение и честно
писать, что действие необратимо.

## Развилка 6: когда обновляется карта

Правка в Neo4j не видна на карте: `pauk/gui/` читает
`data/cache/graph_snapshot.json`, а не базу.

- **Админка читает Neo4j напрямую** (её собственные экраны — живые), а
  карта пересобирается отдельно. Рекомендуется: пересборка — это
  `cache export` + `generate_data` с раскладкой FA2, то есть минуты, а
  не секунды; делать это на каждое сохранение поля бессмысленно.
- **Кнопка «Пересобрать карту»** в разделе обслуживания — тот же
  механизм фоновых задач, что и для запуска пайплайна (ниже). Плюс
  показывать возраст снепшота: `pauk/cache/freshness.py::is_fresh`
  написан ровно под это и сейчас никем не используется.
- Инкрементальный патч `graph-data.js` — не стоит: раскладка
  пересчитывается целиком, точечно её не поправить.

## Развилка 7: запуск пайплайна из UI

- **`subprocess` + коллекция `jobs` в Mongo (рекомендуется).**
  `{_id, command, args, status, actor, started_at, finished_at,
  exit_code, log_path}`; запуск `uv run pauk ...`, лог в файл, UI
  поллит статус или читает хвост лога через SSE. Блокировка: не
  запускать вторую задачу той же команды, пока первая жива.
- **Celery/RQ + Redis** — для одного сервера с редкими ручными
  запусками избыточно.
- **Только показ статуса, запуск руками по SSH** — половинчато, но
  честный первый шаг, если задачи-раннер не хочется писать сразу.

## Развилка 8: модерация дедупа

Три разные функции, разной сложности:

1. **Список «это не дубли»** — коллекция `dedup_blocklist` из пар id,
   которую читают `plan_person_merges` и граф-дедуп. Просто и полезнее
   всего: одна и та же ложная склейка сейчас повторяется каждый прогон.
2. **Ручное слияние** — поверх `merge_*_nodes_batch` плюс запись
   `merged_ids` (иначе воскреснет) и, в идеале, в prepared-документ,
   чтобы дедуп-стадия знала.
3. **Разделение ошибочно слитых** — самое дорогое: требует снимка до
   слияния (см. развилку 5). Планировать последним, не обещать заранее.
