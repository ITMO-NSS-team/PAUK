## Решения, принятые до начала

- **Воркер — отдельный процесс.** Перезапуск панели не обрывает публикацию.
- **Ручные правки во время задачи над графом: предупреждать, но пускать.**
  Расхождение потом видно на экране решений, механизм для этого уже есть.

## Архитектура

```
панель  --(кладёт Job)-->  [ jobs в Mongo ]  <--(забирает)--  воркер
   |                            |                                |
   +---- читает состояние ------+                                |
                                                                 v
                         PipelineRunner.run / load_jsonl_group /
                         run_graph_dedup / пересборка карты
                                                                 |
                          замок ресурса ("graph", "group:2024") --+
                                       ^
                                       |
                          его же берут CLI-команды
```

Панель никогда не выполняет работу в обработчике запроса и **никогда не
собирает командную строку из формы**. Диспетчер `JobKind → функция`,
нагрузка проверена pydantic — та же дисциплина закрытых списков, что уже
работает в [mutations.py](../../pauk/graph/mutations.py).

## Модель данных

`pauk/jobs/models.py`, рядом по стилю с `ProcessingState`:

```python
class JobKind(StrEnum):
    COLLECT = "collect"      # PipelineRunner.run
    PUBLISH = "publish"      # load_jsonl_group
    DEDUP = "dedup"          # run_graph_dedup
    MAP = "map"              # снимок -> данные -> статистика

class JobState(StrEnum):
    QUEUED = "queued"
    CLAIMED = "claimed"      # воркер взял, ресурс ещё не захвачен
    RUNNING = "running"
    DONE = "done"
    FAILED = "failed"
    CANCELLED = "cancelled"
```

`Job`: `kind`, `state`, `payload`, `actor`, `created_at`, `started_at`,
`finished_at`, `heartbeat_at`, `result: dict[str, int]`, `error: str | None`,
`cancel_requested: bool`, `worker: str | None`.

Нагрузка типизирована по виду задачи: `PublishPayload(group: str)`,
`CollectPayload` с тем же выбором, что у `_selector` в CLI,
`MapPayload(public: bool, seed: int)`. Валидация группы — существующим
`validate_group`.

## Замок

Отдельная коллекция, `_id` — имя ресурса. Вставка и есть захват: дубль `_id`
даёт `DuplicateKeyError`, гонки нет.

Частичный уникальный индекс (`unique=True, partialFilterExpression={"state":
"running"}`) отпадает — **проверил, mongomock его не поддерживает**: вызов
падает с `DuplicateKeyError` уже на создании. Тесты на нём писать нельзя.

Ресурсы: `graph` (публикация, дедуп, снимок) и `group:<имя>` (сбор по группе).
Сбор по разным группам параллелится, запись в граф — нет.

Срок жизни по `heartbeat_at`: убитый воркер иначе заклинит очередь навсегда.

**Замок берут и CLI-команды, а не только воркер.** Иначе он не защищает от
самого частого случая: человек запускает `pauk publish graph` в терминале,
пока панель ставит свою задачу. Значит замок живёт в `pauk/graph/`, а
`load_jsonl_group` и `run_graph_dedup` берут его сами — обе уже принимают
`mongo_db`, новых зависимостей не появляется.

## Захват задачи

1. `find_one_and_update({state: queued}, {$set: {state: claimed, worker, ...}})`
   — атомарно, задача достаётся одному воркеру. Проверил, mongomock это умеет.
2. Захватить замок ресурса. Занят — вернуть задачу в `queued` и подождать.
3. Выполнить, обновляя `heartbeat_at`; записать `result` или `error`;
   отпустить замок.

## Этапы

### 1. Очередь, замок и его подключение к CLI

`pauk/jobs/models.py`, `pauk/jobs/store.py`, `pauk/jobs/locks.py`, индексы в
`ensure_indexes`, замок внутри `load_jsonl_group` и `run_graph_dedup`.

Готово, когда: две одновременные публикации невозможны, и это покрыто тестом.
Панели и воркера ещё нет, но безопасность уже выросла — сейчас два `publish`
разом ничем не разведены.

### 2. Воркер

`pauk admin worker`: цикл, диспетчер `JobKind → функция`, heartbeat, отмена
между шагами, аккуратное завершение по сигналу.

Готово, когда: задача, положенная в Mongo руками, выполняется и её результат
виден в записи.

### 3. Карта: вынести ядро и путь вывода

`generate_data.main()` → `write_graph_files(snapshot, out_dir, seed, public)`.
У `generate_stats` ядро уже есть (`snapshot()` и `write_js`) — хватит тонкой
обёртки `write_stats(out_dir)`.

Каталог вывода сейчас захардкожен **внутрь репозитория**
(`pauk/gui/data/private`, [generate_stats.py:34](../../pauk/gui/generate_stats.py#L34)).
Воркер, пишущий туда, пишет в рабочую копию. Вынести в `Settings` рядом с
`cache_dir`, значение по умолчанию оставить прежним — существующие команды
не меняются.

Готово, когда: карта собирается вызовом функции, CLI остаётся тонкой обёрткой,
поведение команд не изменилось.

### 4. Панель: только чтение

Страница `/jobs` — очередь и история, теми же идиомами фильтров и страниц,
что уже сделаны для журнала. Полоса-предупреждение на карточках, пока идёт
задача над графом. Кнопок ещё нет.

Закрывает записанный в `docs/admin-panel.md` пробел «панель не знает, идёт ли
публикация прямо сейчас». Полезно само по себе и ничем не рискует.

### 5. Панель: запуск

Формы под замком роли `admin` — и роль наконец начинает отличаться от
`editor`, что в документации значится известным ограничением. Значения только
из списков: группа из существующих в Mongo, вид задачи из `JobKind`, даты
через готовые селекторы. CSRF как везде, `actor` пишется в задачу.

### 6. Отмена, сбои, документация

Снятие протухшего замка, перезапуск упавшей задачи, раздел в
`docs/admin-panel.md`.

## Типы на стыках

Мы на этом обжигались дважды, поэтому закладываю сразу:

- время писать через `_now()` с обрезкой до миллисекунд, как в
  [auth.py](../../pauk/admin/auth.py) и
  [overrides.py](../../pauk/graph/overrides.py) — иначе прочитанный документ
  не равен записанному;
- даты из pymongo приходят без зоны, сравнивать через `_aware()`;
- `Path` хранить строкой, на запись `model_dump(mode="json")`, на чтение
  `Job.model_validate`;
- двойники в тестах держать вровень с настоящими клиентами: расхождение уже
  дважды прятало настоящую ошибку.

## Перепроверка: что оказалось не так, как я думал

- **`load_jsonl_group` не возвращает ничего.** Я собирался хранить в задаче
  тот же словарь счётчиков, что и у остальных шагов, — у публикации его нет.
  Либо страница задач по публикации будет пустой, либо функция должна начать
  возвращать счётчики. Внутри они есть: `apply_overrides` отдаёт свои, число
  узлов и связей логируется. Предлагаю вернуть `dict[str, int]` — правка
  небольшая и делает шаги однородными.
- **Рефактор статистики почти не нужен.** Я записал `generate_stats.main()` в
  работу наравне с `generate_data`, но `snapshot()` и `write_js` там уже
  отдельные функции. Работы меньше, чем я сказал вчера.
- **Частичный уникальный индекс не годится** — mongomock его не тянет.
  Проверено запуском, не по документации.
- **Замок обязан быть в `pauk/graph/`, а не в воркере.** Иначе он не
  закрывает самый вероятный случай — запуск из терминала параллельно с
  панелью.
- **Статистика ходит в Neo4j своим драйвером**, мимо общего `SharedGraph`.
  Для отдельного процесса это нормально; сводить их вместе не нужно, но знать
  стоит.
- **Перечисления групп в коде нет.** Строки помечены массивом `groups`
  ([prepared.py:47](../../pauk/storage/prepared.py#L47)), так что для формы
  понадобится `distinct("groups")` — небольшая новая функция в хранилище.

- Сколько воркеров держать. План рассчитан на одного; на нескольких он тоже
  работает (захват атомарный, замок по ресурсу), но проверять это сейчас
  незачем.
- Показывать ли на странице задач ход выполнения внутри шага. Пока только
  `heartbeat_at`, чтобы зависшая задача была видна; построчный прогресс —
