# RAG по графу (`pauk/rag`)

**Что здесь:** поиск экспертов по свободному вопросу через векторный и
полнотекстовый поиск в Neo4j, сборка экспертов по связям графа, ответ LLM
со ссылками на найденное; построение индексов профилями и валидация с
абляциями.

**Какие файлы задействует:** `pauk/rag/*.py`, `pauk/sources/github.py`
(`get_readme`), `pauk/urls.py` (`github_owner_name`); на диске —
`data/rag/` (кэш README, кэш векторов, манифесты профилей, прогоны валидации;
каталог в `.gitignore`).

## Поток

```
вопрос
  │ extract_keywords (LLM) или query_keywords извне → английские ключевые слова
  │ embedder.encode / escape_lucene
Neo4j: vector index + full-text index профиля   retrieve: dense | bm25 | hybrid
  │ топ-k публикаций и репозиториев с баллами
Neo4j: AUTHORED, CONTRIBUTED_TO                  experts: Σ relevance² по работам человека
  │
LLM                                              answer: текст с [n] только на найденные источники
```

По умолчанию и BM25, и энкодер получают английские ключевые слова вопроса, а не
сам вопрос (см. «Режимы поиска» и результаты ниже); при сбое LLM поиск идёт по
вопросу как есть с заметкой в `notes`. Фильтры (годы, подразделения) RAG не
применяет — это слой шаблонов text-to-Cypher.

## Профили индекса (`profiles.py`)

Профиль — какие поля узла образуют встраиваемый текст. Единица абляции:
два профиля, различающиеся одним полем, строятся рядом и сравниваются на
одних вопросах.

| Узел | Поля |
|---|---|
| `Publication` | `title`, `abstract`, `fields` (домены OpenAlex), `journal`, `full_text` (первые 2000 символов) |
| `Repository` | `name`, `description`, `readme` (очищенное начало, ≥20 слов), `readme_raw` (как отдаёт GitHub), `implemented` (названия реализуемых статей) |

Пресеты: `full` (обоснованный выбор) и варианты, меняющие в нём ровно одно —
`no_readme`, `raw_readme`, `no_implemented`, `with_fields`, `with_full_text`,
плюс нижняя граница `title_only`. Произвольный профиль — через
`--publication-fields` / `--repository-fields`.

Почему такой `full` (по данным на 2026-10-06): аннотация есть у 81% статей
(медиана 1030 символов — целиком входит в окно модели); у репозиториев
описание короткое (медиана 65 символов), `topics` в графе нет вовсе, README
есть у 384 из 409 и почти всегда информативнее описания; 14 репозиториев без
описания и README, 11 из них реализуют статью — их находят только по
`implemented`. Записи типов `paratext`, `peer-review` и рисунки без аннотации
(`other`, `dataset`) не индексируются: короткая подпись вроде «Graphical
Abstract» близка к любому расплывчатому вопросу.

## Хранение в Neo4j (`graph.py`, `index.py`)

На узел профиля `p` и модели `m`: `rag_text_p` (собранный текст, общий для
всех моделей), `rag_vec_p_m` (float32, через `db.create.setNodeVectorProperty`),
`rag_hash_p_m` (sha1 модели и текста). Индексы: `rag_vec_p_m_<label>`
(векторный, cosine, свой у каждой модели) и `rag_text_p_<label>`
(полнотекстовый Lucene, один на профиль — BM25 от модели не зависит; ранжирование BM25, анализатор
`english`: стоп-слова и стемминг английского; русский вопрос к нему идёт через
английские ключевые слова).

- `pauk publish` пишет узлы через `SET n += ...` и `rag_*` не трогает. Если у
  узла изменился текст, его хэш перестаёт совпадать, и следующий `pauk rag
  index` пересчитает только его.
- Векторы кэшируются на диске по хэшу текста (`data/rag/vectors/`): профили с
  одинаковыми полями статей не встраивают 13 тысяч аннотаций заново.
- `pauk rag drop --profile p` удаляет свойства и индексы профиля целиком,
  `--model m` — только векторы одной модели. Манифест — `data/rag/profiles/p@m.json`.
- `queryNodes` векторного индекса возвращает cosine, приведённый к [0, 1] как
  (1 + cos) / 2 (и `SEARCH`, которым он запрашивается, тоже); для ранжирования это не важно, для чтения сырых баллов — да.

## Режимы поиска (`retrieve.py`)

- `dense` — векторный индекс; находит по смыслу, в том числе русский вопрос
  к английской аннотации.
- `bm25` — полнотекстовый индекс по словам вопроса (операторы Lucene
  экранируются: `RT-DETR` — не «RT без DETR»). Русский вопрос к английскому
  тексту совпадает только по названиям и числам — это ожидаемое ограничение
  режима, а не ошибка.
- `hybrid` — обе выдачи на глубину 2k, каждая min-max нормируется,
  0.7·dense + 0.3·bm25; `--fusion rrf` — reciprocal rank fusion по рангам.

Ключевые слова: по умолчанию `ask` извлекает их сам (`extract_keywords`,
кэш в `data/rag/keywords.json`). Вызывающий код, у которого они уже есть,
передаёт их в `query_keywords` — так планировщик text-to-Cypher получает их
в своём вызове LLM и экономит второй. Правила одни: `KEYWORDS_RULES`
вставляется в промпт планировщика. Валидация (`pool`) всегда извлекает
ключевые слова сама, поэтому метрики относятся к `extract_keywords`;
ключевые слова планировщика перед доверием стоит сравнить с ними на той же
выборке.

Эксперты (`Rag.experts`): балл человека — сумма по его найденным работам
(релевантность, нормированная внутри типа)²; репозиторий весит 0.5 статьи.
Квадрат — чтобы одна точная работа перевешивала несколько смежных.

## Пустой ответ

Векторный поиск всегда возвращает ближайших соседей, даже если по теме в
графе ничего нет. Поэтому у модели есть порог `min_score` (`models.py`, в
шкале индекса (1 + cos) / 2): если лучшее совпадение типа ниже порога, `ask`
убирает этот тип из выдачи, а если пусто всё — отвечает «по теме ничего не
найдено» без вызова LLM (`--no-abstain` отключает).

Порог задаётся не по валидации, а по отдельным вопросам на темы, которых в
графе нет (`data/rag/calibration/offtopic.csv`, 40 вопросов): это 95-й
перцентиль их лучших совпадений, то есть около 5% таких вопросов всё же
получат ответ (`pauk rag calibrate --variant …`). Порог верен только для
того запроса, на котором откалиброван, — у `ask` по умолчанию это ключевые
слова и в BM25, и в эмбеддер. На валидации, которую калибровка не видит,
`pauk rag metrics` печатает число правильных и ошибочных пустых ответов.

Валидация 2026-10-16 (100 вопросов, вариант `hybrid:en+kw`, профиль `full`):

| модель | `min_score` | верно пустых из 11 без ответа | ошибочно пустых из 89 |
|---|---|---|---|
| Qwen3-Embedding | 0.770 | 9 | 1 (0 у `raw_readme` и `no_readme`) |
| Arctic-Embed-L v2.0 | 0.696 | 8 | 2 |
| BGE-M3 | 0.798 | 9 | 21 |

## Валидация (`evaluation.py`)

Вариант — `профиль[@модель]:режим[:опции]`, опции через `+`: `en` — ключевые
слова в BM25, `kw` — ключевые слова в энкодер, `rrf` — слияние по рангам
(например `full@qwen3:hybrid:en+kw`; без `@` — bge-m3). Вопросы читаются из
общего банка (`questions.csv`), где есть и графовые (`q…t1`), и смешанные
(`q…t2`) вопросы — их маршрутизирует отдельный пайплайн; по умолчанию берётся
только семантическая группа `q…t3`. Группа определяется по `id`, а не по `type`
(`no_answer` есть в каждой группе); строки без такого `id` — например
off-topic вопросы для `calibrate` — берутся все. Пайплайн смешанных вопросов
собирает пул тем же кодом: `pauk rag pool --groups 2 --keywords-file <его
keywords.json> --run-dir <его каталог>` (`--run-dir` есть и у `judge`, `tails`,
`metrics`); ручные ключевые слова берутся по `id` вопроса, по умолчанию из
`data/rag/keywords.json`. Все варианты отвечают на все вопросы;
топ-k людей, публикаций и репозиториев объединяются в пул (TREC-пулинг),
размечается только пул (0/1/2). Вопрос без единого релевантного элемента
некоторого типа в метрики этого типа не входит. Cutoff'ы задаются `--k`
(по умолчанию 5 и k пула) и не могут превышать k, с которым собран пул: глубже
нет ни выдачи, ни оценок. Recall@k — пуловый: в знаменателе релевантные
элементы, найденные хоть одним вариантом, а не все релевантные в графе, поэтому
он завышен и годится для сравнения вариантов, а не для оценки полноты.
`compute_metrics` даёт P@k, R@k, nDCG@k, MRR, judged@k по типу и варианту
(только для типов, которые вопрос спрашивает — колонка `targets`), а с
`--baseline` — знаковый тест по вопросам (wins, losses, двусторонний p) по nDCG
на наибольшем cutoff. Согласие двух оценщиков (`--judge X --against Y`, без
`--against` — с ручной разметкой `judgments.json`): доля совпадений, κ Коэна,
взвешенная κ и её 95% интервал бутстрепом по вопросам.

## LLM-разметка

Судья (`judge_pool`) оценивает публикации и репозитории по одному на
запрос, промптом `JUDGE_SYSTEM` (текст методики, 2026-10-16): вопрос, правило
релевантности и один элемент — у публикации название, аннотация и первые
3000 символов полного текста, у репозитория название, описание и первые
3000 символов README как есть (не очищенного: абляцию README нельзя
оценивать через её же предобработку). Людей судья не оценивает: их оценка —
максимум оценок их работ, это делает код.

Для внешней проверки рядом с оценками лежат `judge_<judge>.config.json`
(модель, текст и id промпта, лимиты, прогоны) и `judge_<judge>.log.jsonl` —
каждый запрос с точным сообщением, сырым ответом и токенами. Один файл
оценок — один судья: другая модель или промпт в тот же `--judge` не пишет.

Пул хранит ключевые слова, с которыми искали варианты (`keywords`: текст,
LLM и id промпта), — он не зависит от кэша `keywords.json`. Судьям ключевые
слова не показываются: судья, читающий формулировку системы, оценивал бы по
ней.

Если человек попал в выдачу через работу, которой нет в пуле вопроса
(репозиторий в вопросе про людей), пул хранит её в `extra`, и судья оценивает
и её: оценка человека всегда опирается на размеченные работы.

Для рассуждающих моделей (GPT-6 Luna) — `--reasoning-effort minimal`: модель
думает в пределах `max_tokens`, и без этого ответ может прийти пустым.

Глубина пула — 50. Её выбрали по хвостам (`pauk rag tails`, прогон `tails`):
10 вопросов разных типов, 21 вариант, пул глубиной 100. Правило «глубина =
последний релевантный элемент» дало 100: на широких темах частично релевантные
работы идут до конца списка. При глубине 50 пул покрывает 94–100% прямо
релевантных (оценка 2) работ на узких, глубоких, кодовых и перефразированных
вопросах и 55–68% на широких — для них recall неполный при любой разумной
глубине.

Прогоны в `data/rag/runs/`: `validation` (100 вопросов, 25 вариантов, судьи
`qwen50` и `luna`), `human_check` (6 вопросов, 184 работы — ручная разметка
для каппы с судьями), `tails` (замер глубины), `conditions` (6 вопросов с
ограничением по годам или подразделению — для слоя шаблонов, RAG их не решает).

## Команды

```bash
uv run pauk rag readmes --seed data/search/readmes       # кэш README (сеть только для недостающих)
uv run pauk rag index --profile full                     # построить / обновить профиль
uv run pauk rag index --profile no_readme
uv run pauk rag index --profile full --model qwen3       # тот же профиль, векторы другой модели рядом
uv run pauk rag profiles                                 # пресеты, поля, что построено
uv run pauk rag ask "кто занимается федеративным обучением" --no-answer   # qwen3, ключевые слова в BM25 и в эмбеддер; --no-dense-keywords, --no-keywords
uv run pauk rag ask "кто занимается федеративным обучением" --keywords "federated learning" --no-answer   # свои ключевые слова, без вызова LLM
uv run pauk rag pool --run validation --variants "$(cat data/rag/runs/validation/variants.txt)" --k 50
uv run pauk rag pool --run validation                    # без --variants: те же варианты, что уже в пуле
uv run pauk rag judge --run validation --judge qwen50 --workers 12          # судья из PAUK_LLM_MODEL
uv run pauk rag judge --run validation --judge luna --model openai/gpt-6-luna --reasoning-effort minimal --workers 12
uv run pauk rag judge --run validation --judge luna --model openai/gpt-6-luna --reasoning-effort minimal --limit 10   # проба
uv run pauk rag metrics --run validation --judge qwen50 --baseline full:hybrid:en+kw --k 10,50
uv run pauk rag metrics --run validation --judge luna --against qwen50    # + согласие двух судей
uv run pauk rag metrics --run human_check --judge qwen50                  # согласие с ручной разметкой
uv run pauk rag tails --run tails --judge qwen        # позиция последнего релевантного по вариантам -> глубина пула
uv run pauk rag drop --profile no_readme
```

## Модели эмбеддингов (`models.py`)

`--model` у `index`, `ask` и `drop`; по умолчанию — `PAUK_RAG_EMBEDDING_MODEL`
(`Qwen/Qwen3-Embedding-0.6B`, с 2026-10-15). В валидации модель — часть
варианта: `full@qwen3:dense`; вариант без `@` — всегда bge-m3, а не модель по
умолчанию, чтобы размеченные варианты не меняли смысл при смене умолчания. `Rag.profile` не даёт искать векторами модели,
которой профиль не собран: вопрос и документы должны быть встроены одной
моделью, иначе поиск молча вернёт шум.

| alias | модель | параметры | префикс вопроса |
|---|---|---|---|
| `bge` | `BAAI/bge-m3` | 568M, 1024 | — |
| `arctic` | `Snowflake/snowflake-arctic-embed-l-v2.0` | 568M, 1024 | `query: ` |
| `qwen3` | `Qwen/Qwen3-Embedding-0.6B` | 600M, 1024 | `Instruct: <задача>\nQuery:` |

`arctic` — та же основа XLM-R large, что у bge-m3; `qwen3` — эмбеддинги на
основе LLM. Инструктивные модели обучены с задачей перед вопросом (документы —
без префикса); без неё они заметно проседают.

`intfloat/multilingual-e5-large-instruct` проверялась и исключена (2026-10-14):
nDCG@10 по людям 0.20 против 0.65 у bge-m3 в режиме dense, проигрыш на 22 из 23
вопросов. Модель тянется к языку вопроса: на «Кто занимается федеративным
обучением?» наверху русские тексты про обучение в смысле образования, а не
английские статьи про federated learning; инструкция перед вопросом этого не
исправляет.

Зависимость — extra `rag` (`sentence-transformers`).

## Результаты валидации (2026-10-16)

Прогон `data/rag/runs/validation`: 100 вопросов (69 про людей и публикации, 24
про код, 11 без ответа; 6 вопросов с годами или подразделением вынесены в
`conditions`), 25 вариантов, пул глубиной 50 — 20 121 работа. Разметили два
судьи по одному промпту: Qwen2.5-72B-Instruct (`qwen50`) и GPT-6 Luna (`luna`).
Полные таблицы — `results_qwen50.md` в прогоне; ниже nDCG@10 (Qwen / Luna),
база — bge `full:hybrid:en+kw`, p — знаковый тест по nDCG@10 (Luna):

| вариант | люди | публикации | репозитории |
|---|---|---|---|
| `full:bm25` (вопрос как есть) | 0.130 / 0.106 | 0.096 / 0.072 | 0.126 / 0.104 |
| `full:bm25:en` | 0.797 / 0.782 | 0.719 / 0.678 | 0.690 / 0.689 |
| `full:hybrid` (без ключевых слов) | 0.749 / 0.721 | 0.615 / 0.576 | 0.570 / 0.543 |
| `full:hybrid:en+kw` (база) | 0.823 / 0.806 | 0.726 / 0.697 | 0.721 / 0.706 |
| `full@arctic:hybrid:en+kw` | 0.895 / 0.876 | 0.817 / 0.783 | 0.764 / 0.744 |
| `full@qwen3:dense:kw` | 0.910 / 0.905 | 0.823 / 0.795 | 0.792 / 0.777 |
| **`full@qwen3:hybrid:en+kw`** | **0.902 / 0.905** (p < 0.001) | **0.845 / 0.811** (p < 0.001) | **0.805 / 0.791** (p = 0.003) |
| `raw_readme@qwen3:hybrid:en+kw` | 0.902 / 0.904 | 0.845 / 0.811 | 0.830 / 0.816 |
| `no_readme@qwen3:hybrid:en+kw` | 0.904 / 0.904 | 0.845 / 0.811 | 0.748 / 0.745 |

- Qwen3 лучше всех и значимо лучше базы; порядок Qwen3 > Arctic > bge-m3.
- Ключевые слова необходимы BM25 (0.13 → 0.80 по людям) и гибриду с bge;
  энкодеру bge почти ничего не добавляют.
- С сильным энкодером BM25 почти ничего не даёт: dense Qwen3 ≈ hybrid Qwen3.
- README нужен для поиска кода (без него хуже у всех моделей). Эффект очистки
  README зависит от модели (Qwen3: сырой лучше, Arctic: очищенный лучше, bge:
  без разницы) и на 24 вопросах после поправки на три сравнения не значим.
- Судьи согласны: взвешенная κ = 0.78 [0.75; 0.81] на всём пуле (0.67 на
  184 работах `human_check`); порядок 25 вариантов по nDCG@10 совпадает
  (τ Кендалла 0.97 / 0.91 / 0.95), лучший вариант у обоих один. Luna строже:
  её значения на 0.01–0.04 ниже.
- Ограничения: обе разметки — LLM, согласие с человеком меряется на
  `human_check`; Qwen2.5 и судит, и извлекает ключевые слова; recall на
  широких темах неполный; 24 вопроса про код; один университет.
