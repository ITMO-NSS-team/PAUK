# `pauk/search/` — вопрос к графу на естественном языке

**Что здесь:** как свободный вопрос («кто в ИТМО занимается диффузионными
моделями?», «сколько публикаций у X?») превращается в людей, подразделения,
публикации и репозитории из графа. Где лежит индекс и почему граф при этом
не меняется.

**Какие файлы задействует:** `pauk/search/*.py`, `pauk/gui/serve.py`
(`POST /api/ask`), `pauk/gui/web/tab-ask.js`.

## Главный принцип

LLM не пишет запросов к графу и не строит граф. Она только разбирает вопрос
в план (LLM №1) и оформляет готовый результат в текст (LLM №2). Всё между
ними детерминировано: точки входа ищутся по индексу, связи извлекаются
фиксированными Cypher-шаблонами, ранжирование и обрезка — код. Шаблоны
универсальные: достают вокруг точек входа больше, чем нужно конкретному
вопросу, а лишнее отсекается кодом. Отсечь лишнее дёшево, а то, что запрос не
достал, уже не восстановить.

## Поток одного вопроса (`pipeline.py::Engine.ask`)

```
вопрос
  → LLM №1 (llm.parse_question) → QueryPlan (plan.py), при сбое — поиск по всему вопросу как по теме
  → type = topic / graph / mixed (выводится из плана: есть core → тема, есть entities → граф, оба → смешанный)
      topic : core → retrieval по публикациям и репозиториям → topic_subgraph
      graph : entities → entities.NameIndex.resolve → person_profile / department_profile
      mixed : сущность → её публикации → retrieval только среди них → topic_subgraph
  → ranking.rank + ranking.trim (по expected_values / fields / filter)
  → LLM №2 (llm.compose_answer): текст только по отобранным строкам
```

`QueryPlan` — тот же JSON, что на схеме архитектуры: `type`, `entities`,
`expected_values`, `fields`, `filter`, `core`, `graph_type`. Значения —
английские коды, чтобы код ветвился по ним надёжно. `type` пересчитывается
валидатором из содержимого плана, а не берётся на веру у модели. Поля из
`fields`, которых нет в белом списке `plan.FIELDS`, игнорируются.

## Только чтение графа (`reader.py`)

Поиск не имеет права менять граф: восстановление — это полная публикация
всех групп. Две независимые защиты: каждый запрос идёт в read-транзакции
(`execute_read`, `READ_ACCESS` — Neo4j сам откажет в записи), и запрос с
пишущей конструкцией (`CREATE`, `MERGE`, `SET`, `DELETE`, `REMOVE`, `DROP`,
`LOAD CSV`, `CALL { } IN TRANSACTIONS`) отклоняется ещё до отправки.

## Индекс (`index.py`, `readme.py`) — `data/search/`

Эмбеддинги хранятся не в Neo4j, а файлами в `<data_dir>/search`: векторное
свойство и векторный индекс изменили бы граф, а следующий `pauk publish`
или `dedup graph` мог бы их потерять при слиянии узлов. При ~14 тысячах
публикаций numpy-матрица в памяти не медленнее векторного индекса.

| Файл | Что в нём |
|---|---|
| `publications.npy` / `.json` | вектор и текст на публикацию: `title + abstract` (без аннотации — `title + fields`) |
| `repositories.npy` / `.json` | вектор и текст на репозиторий: `name + description + topics + README` |
| `persons.json`, `departments.json` | имена для поиска сущностей. **Персональные данные — каталог в `.gitignore`** |
| `readmes/*.md` | тексты README из GitHub API: в графе есть только флаг `has_readme` |
| `manifest.json` | модель, дата сборки, счётчики |

Модель — `PAUK_SEARCH_EMBEDDING_MODEL`, по умолчанию `BAAI/bge-m3`:
мультиязычная, поэтому русский вопрос сопоставляется с английскими
аннотациями без перевода. Смена модели требует пересборки индекса — та же
модель кодирует и документы, и вопрос.

Индекс — снимок графа на момент сборки. После `publish`/`dedup graph`
его стоит пересобрать, иначе новые узлы не найдутся, а слитые id могут
не совпасть с графом.

## Точки входа (`retrieval.py`)

Три режима, оставлены рядом ради сравнения в оценке: `bm25` (совпадение
слов), `dense` (косинус эмбеддингов), `hybrid` (0.7 × эмбеддинги + 0.3 ×
BM25). Без установленного `sentence-transformers` поиск откатывается на
`bm25` и говорит об этом в заметках к ответу.

Несколько фраз `core` сливаются в один запрос — нормированное среднее их
векторов. Лучшее совпадение по каждой фразе отдельно позволяло побеждать
самой многозначной: «диффузионные модели» сама по себе тянет диффузию
ионов и массоперенос.

Релевантность, которую точка входа несёт дальше, нормируется внутри списка
(min-max). Косинусы bge-m3 лежат в узкой полосе (≈0.52–0.66 на топ-300), и
без нормировки сотая статья весила бы почти как первая — человек с
десятком слабо похожих работ обходил бы автора одной точно попавшей.

## Сущности по имени (`entities.py`)

Полнотекстового индекса в Neo4j нет и создавать его нельзя (это изменение
графа), поэтому имена ищутся в памяти, `rapidfuzz.token_set_ratio`. Каждое
имя сравнивается в единой латинской форме: вопрос обычно по-русски,
OpenAlex пишет латиницей, а русские поля заполнены не у всех. Инициалы
(«Иванов И.») отсекают кандидатов с другим именем. Сотрудники ИТМО выше
внешних соавторов; почти равные кандидаты помечаются как неоднозначные, и
ответ показывает варианты.

## Шаблоны (`templates.py`)

`topic_subgraph` — авторы, подразделения (`PRODUCED_BY` и иерархия
`PART_OF`), репозитории (`IMPLEMENTS`, `CONTRIBUTED_TO`) вокруг найденных
публикаций и репозиториев. `person_profile` — все публикации, репозитории и
соавторы человека. `department_profile` — подразделение с дочерними,
их публикации и сотрудники.

## Ранжирование (`ranking.py`)

Релевантность входит только через узлы с текстом (публикации, репозитории);
люди и подразделения получают её по рёбрам:

```
балл(человек) = Σ по его найденным публикациям: релевантность² × вес позиции × вес свежести
              + 0.5 × релевантность² каждого репозитория, где он контрибьютор
```

Квадрат (`relevance_power`) нужен, чтобы одна точно попавшая работа весила
больше нескольких слабых: с первой степенью на вопрос о диффузионных
моделях наверх выходили химики с тремя статьями о диффузии ионов.

Вес позиции — 1 для первого и последнего автора, 0.5 для остальных; свежесть
— полураспад 4 года. Подразделение получает публикацию один раз, где бы
ниже по иерархии она ни была сделана, но с затуханием 0.3 на каждый уровень
вверх: без него мегафакультет, складывающий все свои лаборатории, всегда
стоял бы выше лаборатории, которая сделала работу. Пресет `authorship` выключает
позицию, свежесть, код и иерархию — классическая модель «через документы»
для сравнения. Затем `trim` оставляет запрошенные разделы, поля и `top_n`.

## LLM (`llm.py`)

Клиент — общий `pauk/sources/llm.py::OpenRouterClient` (модель
`PAUK_LLM_MODEL`, прокси `OPENROUTER_PROXY_URL`). LLM №2 получает только
обрезанный результат; ссылку, которой нет в этих данных, `strip_unknown_links`
превращает в обычный текст. Оба вызова можно выключить (`--no-llm-parse`,
`--no-llm-answer`, флажки во вкладке) — для экспериментов и оценки без
расхода токенов.

## Прогон пачкой (`batch.py`) — разбор ошибок и оценка

`pauk search batch questions.csv` задаёт каждый вопрос из файла и пишет в
`<data_dir>/search/batch/` (или `--out`) два файла:

- `results.jsonl` — полный ответ на каждый вопрос (план, кандидаты сущностей,
  точки входа, разделы, заметки, время) для детального разбора;
- `review.csv` — строка на вопрос: как система поняла вопрос и верх каждого
  раздела, плюс пустые колонки `correct`, `broken_step`, `comment`.
  `broken_step` — шаг, на котором сломалось: `parse | entities | retrieval |
  template | ranking | answer | data | unsupported`. Открывается в Excel и
  Google Sheets как есть.

Вход — `.txt` (вопрос на строку, `#` — комментарий) или `.csv` с колонкой
`question` и необязательными `type` (категория вопроса) и `expected` (что
должно быть в верном ответе). По умолчанию вопрос проходит весь путь, обе LLM включены: ошибки разбора
и текст ответа — тоже то, что размечаем. `--no-llm-parse` и
`--no-llm-answer` выключают их, чтобы не тратить токены.
Ответы, уже полученные с теми же настройками, берутся из `results.jsonl`,
поэтому повторный прогон тратит токены только на новые вопросы (ответ,
где вызов LLM не удался, переспрашивается: иначе сбой сети застрял бы в
прогоне навсегда); `--force`
переспрашивает всё. Разметка в `review.csv` при повторном прогоне
сохраняется.

Смотреть и размечать прогоны удобнее на странице разработчика
`http://localhost:8501/review` сервера карты (`pauk/gui/web/review.html`,
`review.js`): слева вопросы с оценкой, справа ответ, разделы, план LLM №1,
кандидаты сущностей, точки входа и время по этапам. Оценка, шаг поломки и
комментарий сохраняются в тот же `review.csv`, так что CLI и страница
работают с одним файлом. Клавиши: ↑/↓ — вопросы, 1/2/3 — да/частично/нет.
Страница видит все прогоны под `<data_dir>/search` и не открывается в
`--public`: в ней имена людей.

## Сравнение вариантов (`evaluation.py`) — пулинг

Полную разметку всех 13 тысяч публикаций под каждый вопрос не сделать,
поэтому сравнение устроено как на TREC. `pauk search pool --run batch`
берёт планы LLM №1 из прогона и прогоняет каждый вопрос через варианты
`evaluation.VARIANTS`: `bm25`, `dense`, `hybrid` с ранжированием «только
авторство», и `dense+graph`, `hybrid+graph`. Первые `k` (по умолчанию 10)
людей и публикаций каждого варианта сливаются в один пул; на странице
`/review` в режиме «оценка пула» пул размечается 0 / 1 / 2 (не по теме /
частично / точно). Порядок перемешан, и какой вариант что нашёл, не
показано. Всё, чего не вернул ни один вариант, считается нерелевантным.

`pauk search metrics --run batch` считает по разметке P@5, P@10, nDCG@10,
MRR и долю размеченных в топ-10 (`judged@10`) по каждому варианту и пишет
`metrics.csv`. Полнота (recall) не считается: всего релевантного в базе не
знает никто. Вопросы без темы (профиль, подсчёт) в пул не входят — поиск
по смыслу в них не участвует. LLM при сборке пула не вызывается: план
берётся из прогона.

Файлы рядом с прогоном: `pool.json`, `judgments.json`, `metrics.csv`.
Ключи оценок — `вид:id`, поэтому пересборка пула старые оценки сохраняет.

## Запуск

```bash
uv sync --extra search            # sentence-transformers + torch (несколько ГБ)
uv run pauk search fetch-readmes  # ~400 запросов к GitHub API, по желанию
uv run pauk search build-index    # читает граф, пишет data/search/
uv run pauk search ask "Кто занимается диффузионными моделями?" --no-llm-answer
uv run pauk search batch questions.csv  # пачка вопросов → review.csv для разметки
uv run pauk search pool                 # пул вариантов для оценки на /review
uv run pauk search metrics              # P@k, nDCG, MRR по вариантам
uv run python -m pauk.gui.serve   # вкладка «Вопрос» на карте
```

Вкладка «Вопрос» ходит в `POST /api/ask` сервера карты. Движок (модель
эмбеддингов и индексы в памяти) поднимается в фоне при старте сервера,
если индекс уже собран. В `--public` маршрут закрыт, как `/api/check`:
ответ содержит имена.
