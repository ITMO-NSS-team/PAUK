# `persons` — стейдж

**Что здесь:** как персона обогащается из собственных записей автора и
отдельный Crossref-проход по публикациям в том же стейдже.

**Какие файлы задействует:** `pauk/pipeline/stages/persons.py`.

Обогащает `Person` из собственных записей автора: OpenAlex author API,
ORCID, опционально OpenReview. Плюс отдельный, не связанный по коду
Crossref-проход прямо в этом же стейдже — backfill ORCID у соавторов по
DOI публикации.

## Основной проход — один автор за раз

Для каждого `Person`, требующего внимания (`needs_attempt`):

1. Если есть `openalex_id` — `GET /authors/{id}`: обновляет `name_en`,
   собирает варианты имени (`name_variants`), ORCID (если ещё не известен),
   и аффилиации автора из его собственной записи (`affiliations` +
   `last_known_institutions`, последнее без годов — это фолбэк на случай
   года, для которого нет явной записи).
2. Если есть ORCID — `GET /record`: email (первый найденный, если своего
   ещё нет), аффилиации из ORCID-employments (`start`/`end` год,
   открытая employment покрывает всё от начала до текущего года).
3. `is_itmo` пересчитывается: хотя бы одна аффилиация с ROR ИТМО где
   угодно — человек ИТМО, даже если ни одна конкретная работа этого не
   утверждала (`ITMO_ROR_ID` тот же, что в `normalize.py`).
4. **Заполнение пропущенной аффилиации у авторства**
   (`_fill_missing_affiliations`) — self-deposit площадки (Zenodo, SSRN)
   часто не указывают, где работал конкретный соавтор на момент этой
   работы. Собственные записи автора это знают — подставляется аффилиация,
   покрывающая год публикации (`_affiliation_for_year`: сначала точное
   совпадение по году, затем самая свежая датированная, затем недатированная
   как последний фолбэк), и `affiliation_source` фиксирует, что значение
   *подставлено*, а не заявлено самой работой — на случай если позже придут
   более достоверные данные с явной аффилиацией, которые не должны
   молча проиграть заполненному значению.
5. Если человек ИТМО и заданы `OPENREVIEW_USERNAME`/`PASSWORD` — поиск
   профиля OpenReview по имени; совпадение подтверждается по ORCID или по
   `@itmo.ru`-почте в списке email профиля. При совпадении заполняются
   `openreview`/`github`/`google_scholar` — это **единственный** путь,
   которым `Person.github` вообще заполняется в текущем пайплайне; прямого
   поиска «этот автор → вот этот GitHub-логин» нет.

Без OpenReview-креденшлов шаг 5 тихо пропускается (не ошибка, просто
условие `self.config.openreview_username and ...` не выполняется) — без
`.env.example`-переменных этот стейдж работает, просто уже без
GitHub/Scholar/OpenReview заполнения.

Статус — `COMPLETED`/`COMPLETED_EMPTY` по факту реального изменения полей
(сравнение dump'а до/после, исключая `processing`/`authored`/`contributed_to`),
не по факту успешного HTTP-запроса — запрос мог пройти и не принести
ничего нового.

## Crossref-проход — по публикации, не по автору

Отдельный цикл, ключ резюмируемости — не `Person.processing["persons"]`, а
`Publication.processing["crossref"]`. Для каждой публикации с DOI, чей
Crossref-этап ещё не завершён: `GET /works/{doi}`, для каждого автора из
ответа Crossref — сопоставление по фамилии (`casefold` последнего слова
`name_en`) с локальными `Person` этой публикации; при однозначном совпадении
(ровно один локальный автор с такой фамилией) и отсутствии у него ORCID —
проставляется ORCID из Crossref.

Публикация без DOI сразу помечается `NOT_APPLICABLE` — Crossref без DOI
искать нечего.

Сопоставление идёт по одной фамилии, поэтому дедуп
(`pipeline/stages/dedup.py`) трактует `Person.orcid` как не полностью
авторитетный источник: если для автора есть сырая запись OpenAlex, дедуп
берёт ORCID оттуда, переопределяя (в том числе сбрасывая в `None`) то, что
мог проставить этот Crossref-backfill.
