# Инструкция по разметке вопросов для text-to-Cypher для LLM
**Что здесь:** Инструкция для LLM по генерации и разметке тестовых вопросов, описание каждого из 10 основных типов запросов, описание ключей, тэгов для каждой группы
<br>
После обновления данных/разметки проверить файл с тестовыми данными скриптом validate_questions.py

**Какие файлы задействует:** `pauk/search/validate_questions.py`.

## 1. Задача

К инструкции приложены два файла:

- **docx с вопросами.** Десять разделов (типов запросов). В каждом разделе: название типа, скелет Cypher-запроса и нумерованный список вопросов. Перед разделом 1 может стоять общий список вопросов.
- **Описание схемы графа Neo4j** (узлы, связи, свойства).

Нужно разметить каждый вопрос: какой шаблон (тип 1–10) должен его обработать и какие параметры в него подставляются. Результат — один CSV-файл. Разметка станет эталоном (gold) для оценки пайплайна, в котором LLM по вопросу выбирает шаблон и заполняет параметры, а Cypher затем строится детерминированно. Поэтому разметка должна быть точной и однозначной, а не «приблизительно верной».

Главный принцип. Если часть вопроса нельзя выразить словарём параметров из раздела 5, не отбрасывай её молча. Поставь `type = none` и объясни причину в `note`. Неполные параметры, которые выглядят нормально, — худшая ошибка разметки.

Разметку не нужно угадывать. Если не уверен, выбери наиболее вероятный вариант и добавь тег `needs_review`.

## 2. Формат файла

- Кодировка UTF-8, разделитель запятая, первая строка — заголовок.
- Заголовок ровно такой: `id,split,section,question,type,subtype,type_alt,params,behavior,tags,note`
- В каждой строке ровно 11 полей. Пустое поле всё равно отделяется запятыми, в том числе последнее (`note`): строка может заканчиваться запятой.
- Поля с запятыми, кавычками или JSON берутся в двойные кавычки; кавычки внутри удваиваются (`""`).
- Одна строка CSV — одна строка файла. Переносов строк внутри полей нет.
- Внутри `tags` и `type_alt` значения разделяются точкой с запятой `;`, не запятой.
- В ответе выдай только CSV, без пояснений до и после.

## 3. Колонки

| Колонка | Содержание |
|---|---|
| `id` | `t{раздел}-{номер вопроса в разделе, две цифры}`, например `t3-02`, `t10-07`. Номер берётся по порядку в разделе. |
| `split` | `dev` или `test`, правила в разделе 4. |
| `section` | Номер раздела в docx, где стоит вопрос (1–10). Если вопрос из общего списка перед разделом 1 и такого вопроса нет ни в одном разделе, `section = 0`, а `id = c-{номер}`. |
| `question` | Текст вопроса дословно, как в docx. |
| `type` | Эталонный тип: `1`–`10` или `none`. Обычно совпадает с `section`. Меняй, только если вопрос явно относится к другому типу, и объясни в `note`. |
| `subtype` | Подтип, если он есть: `3a`, `3b`, `3c`, `3d`. Для остальных типов пусто. |
| `type_alt` | Другие допустимые типы через `;`, если вопрос честно двусмысленный. Обычно пусто. |
| `params` | JSON с эталонными параметрами, правила в разделе 5. |
| `behavior` | `answer` (по умолчанию), `clarify` или `refuse`, правила в разделе 6. |
| `tags` | Теги из списка в разделе 7, через `;`. |
| `note` | Короткий комментарий: почему выбран `none`, что неоднозначно, что нужно проверить. |

## 4. Сплит dev/test

Около четверти вопросов должны попасть в `test`. Правило детерминированное:

- Если номер вопроса в разделе делится на 4 (4, 8, 12, …), то `test`; иначе `dev`.
- Исключение для разделов 6 и 7. Многие темы повторяются в обоих («Кто занимается X?» и «Какие публикации есть по X?»). Найди для вопроса пару в другом из этих двух разделов по той же теме. Оба вопроса получают сплит, который определяется номером вопроса в разделе 6. Если пары нет, сплит определяется собственным номером.
- Вопросы с `section = 0` считай по порядку их номеров `c-NN` и применяй то же правило.
- Если один и тот же вопрос встречается в общем списке и в разделе, оставь только строку из раздела.

## 5. Параметры (`params`)

`params` — JSON-объект. Правила:

- Пиши только те ключи, которые есть в вопросе. Не используй `null`. Если ключа нет, он отсутствует.
- Числа пиши числами (`2022`, не `"2022"`).
- Сущности записывай заглушкой с названием из вопроса:
  - подразделение: `"<id института ИИ>"`; для списка `["<id …>","<id …>"]`;
  - человек: `"<id Бухановский А. В.>"` в том виде, как человек назван в вопросе. Если указана только фамилия, пиши только её и добавь тег `ambiguous_name`.
- Идентификаторы потом подставит скрипт. Твоё дело — точно переписать название из вопроса.

### 5.1. Общие ключи

| Ключ | Значение |
|---|---|
| `target` | Что возвращается или считается: `persons`, `publications`, `repositories`. Обязателен для типов 1–10, кроме `none`. |
| `metric` | `list` (кто, какие, где), `count` (сколько), `exists` (есть ли), `ratio` (доля), `avg_per_year`, `avg_per_person`. |
| `dept_id` | Одно подразделение. |
| `dept_ids` | Только в типе 3: два подразделения (подтип `3c`) или одно (подтип `3d`, где подразделение — второй участник пары). |
| `include_subunits` | По умолчанию подразделения ниже по иерархии включаются, и ключ не нужен. Пиши `false`, только если вопрос явно ограничивает «только самим подразделением». |
| `person_ids` | Список людей. |
| `filters` | Список условий `{"field": …, "op": …, "value": …}`. |
| `group_by` | `dept`, `year`, `quarter`, `type`, `degree`. |
| `order`, `limit` | `"order": "desc"` или `"asc"` и `"limit": N`. Правило: суперлатив в единственном числе («самый», «чаще всего», «больше всего», «у какого») даёт `limit: 1`. «Топ-5», «5 подразделений» дают `limit: 5`. |
| `year_from`, `year_to` | Границы периода, включительно. |
| `last_n_years` | «За последние N лет» — только число N. Годы подставит код. |

Операции в `filters`: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `is_null`, `not_null`. Для списковых полей (`other_names`, `pdf_urls`) `not_null` означает «непустой список».

Периоды:

- «с 2022 года» дает `year_from: 2022`.
- «после 2021» дает `year_from: 2022`.
- «до 2020» дает `year_to: 2019`.
- «в 2023 году» дает `year_from: 2023` и `year_to: 2023`.
- «за 2024–2025» или «с 2020 по 2023» дают границы включительно.
- «за 2026» дает `year_from: 2026` и `year_to: 2026`.

### 5.2. Допустимые поля для `filters`

Используй только поля, которые есть в описании схемы графа. Дополнительно разрешены две вычисляемые величины, указанные ниже.

| Тип | Поля |
|---|---|
| 1 (люди) | `degree`, `github`, `google_scholar`, `linkedin`, `orcid`, `homepage`, `other_names`, `is_itmo` |
| 2 (публикации) | `type`, `doi`, `funding`, `pdf_urls`, `journal` |
| 4 (репозитории и люди) | `license`, `stars_num`, `forks_num`, `archived`, `is_fork`, `has_readme`, `language`, `last_updated`, `contributors_count` (число элементов в `contributors`), `owner_type` (тип GitHub-аккаунта-владельца: `user` или `organization`), `role` (роль в `CONTRIBUTED_TO`) |

Значения:

- Степень (`degree`) в графе хранится по-русски: `"к.т.н."`, `"д.т.н."`, `"к.ф.-м.н."`, `"д.ф.-м.н."` и т. п. Правила:
  - Если в вопросе сказано только «кандидат наук» или «доктор наук» без области, пиши категорию: `"candidate"` или `"doctor"`. Билдер сопоставит её со всеми хранимыми значениями по префиксу `к.` или `д.`.
  - Если названа область («кандидат технических наук», «доктор физико-математических наук»), пиши хранимое значение точно в том виде, как оно записано в графе: `"к.т.н."`, `"д.ф.-м.н."`. Если не уверен в написании, пиши категорию и добавь тег `check_value`.
  - «Имеет степень» дает `not_null`, «не имеет степени» дает `is_null`.
  - Для «кандидатов и докторов по отдельности» пиши `group_by: "degree"` и `filters: [{"field":"degree","op":"in","value":["candidate","doctor"]}]`.
- Дата последнего обновления репозитория (`last_updated`): «не обновлялся больше двух лет» дает `{"field":"last_updated","op":"lt","value":{"years_ago":2}}`; «обновлён за последний год» — `op: "gt"` и `years_ago: 1`. Для конкретной даты — строка `YYYY-MM-DD`. Допустимы только `lt`, `lte`, `gt`, `gte`.
- Булевы поля (`archived`, `is_fork`, `has_readme`, `is_itmo`) принимают только `eq` или `ne` и значения `true`/`false`. Числовые поля (`stars_num`, `forks_num`, `contributors_count`) — числа, не строки. Поля-признаки наличия (`github`, `google_scholar`, `linkedin`, `orcid`, `homepage`, `other_names`, `doi`, `funding`, `pdf_urls`) принимают только `is_null` или `not_null`.
- Если значение поля — перечисление, которого нет в описании схемы (например, `type` публикации), пиши как в вопросе (`preprint`, `conference-paper`). Если в вопросе его нет, дай наиболее вероятное английское значение в нижнем регистре и добавь тег `check_value`.
- «Грантовое финансирование» дает `funding not_null`. «Без DOI» дает `doi is_null`. «Открытый доступ к PDF» дает `pdf_urls not_null`. «Есть лицензия» дает `license not_null`, «нет лицензии» — `is_null`.
- «Аккаунт на GitHub» дает `github not_null`; «профиль Google Scholar» — `google_scholar not_null`; «личный сайт» — `homepage not_null`; «альтернативные имена» — `other_names not_null`.
- Для людей без указания подразделения, когда спрашивают про «ИТМО в целом», добавляй `is_itmo eq true`. Если подразделение указано, `is_itmo` не нужен.
- `last_updated` («не обновлялись больше двух лет», «обновлены больше трёх лет назад») записывается относительной датой: `{"field":"last_updated","op":"lt","value":{"years_ago":2}}`. Для месяцев — `{"months_ago": N}`. Абсолютная дата `YYYY-MM-DD` допустима, только если она названа в вопросе.
- «Внешние (не ИТМО)» дает `is_itmo eq false` (тип 1) или `coauthor_is_itmo: false` (тип 3, см. ниже).

### 5.3. Типы 1, 2, 4: фильтр и агрегация

Билдер строит Cypher из параметров, поэтому один шаблон покрывает много вопросов.

**Тип 1 (люди).** `target: "persons"`. Условия: `dept_id` (если назван), `filters`, `metric`, `group_by`, `order`, `limit`.

Особые случаи:

- «У скольких авторов не указано место работы / не заполнен департамент» — подсчитываются все `Person` без связи `BELONGS_TO`: `{"target":"persons","metric":"count","no_dept":true}`. Ключ `no_dept` используется только для этого.
- «Сколько авторов не указано как сотрудники ИТМО» дает `filters: [{"field":"is_itmo","op":"eq","value":false}]`, `metric: "count"`.
- «В каждом подразделении» дает `group_by: "dept"`. «Кандидатов и докторов по отдельности» дает `group_by: "degree"` и `filters: [{"field":"degree","op":"in","value":["candidate","doctor"]}]`.

**Тип 2 (публикации).** `target: "publications"`. Если подразделение не названо, считаются публикации всего ИТМО.

- Доля: `metric: "ratio"` и `ratio_filters` (какие записи считаются в числителе), например доля препринтов: `"ratio_filters":[{"field":"type","op":"eq","value":"preprint"}]`.
- «В среднем в год» дает `metric: "avg_per_year"`. «В среднем на одного сотрудника» дает `metric: "avg_per_person"`.
- «По годам», «по кварталам» — `group_by`.
- «Прирост 2025 к 2024» и другие разности периодов — `none`.

**Тип 4 (репозитории).** `target`: `persons` (кто контрибьютил, кто владеет) или `repositories` (какие репозитории, сколько репозиториев).

- Репозитории подразделения (`DEVELOPED_BY`) дают `dept_id`.
- «В которые внёс вклад человек» (`CONTRIBUTED_TO`) дает `person_ids`.
- «Кто владеет репозиторием» — `OWNED_BY`: используй `target: "persons"` только если ответ — люди ИТМО. Если ответ — GitHub-аккаунт, ставь `none`.
- Условия на репозиторий (`license`, `stars_num`, …) — в `filters`.

### 5.4.```` Тип 3: соавторство (подтипы)
 
Подтип определяется тем, **кто субъект вопроса** (о чьих соавторах или публикациях спрашивают) и **кто партнёр** (с кем сравнивают). Число сущностей в вопросе значения не имеет.
 
| Подтип | Субъект | Партнёр | Ключи | Пример |
|---|---|---|---|---|
| `3a` | 2–3 человека | нет | `person_ids` | «Какие общие соавторы у Бухановского и Калюжной?» |
| `3b` | один человек | любой | `person_ids` (1) | «С кем у Соколова наибольшее число совместных публикаций?» |
| `3c` | подразделение | подразделение | `dept_id` и `partner_dept_id` | «Есть ли общие публикации у института ИИ и центра ИИ в химии?» «Кто из центра X публиковался с авторами из института ИИ?» |
| `3d` | один человек | подразделение | `person_ids` (1) и `partner_dept_id` | «Есть ли у Кравцова совместные публикации с физическим факультетом?» |
| `3e` | подразделение или весь ИТМО | любой | `dept_id` (необязателен) | «Кто из НЦКР имеет наибольшее число различных соавторов?» «Кто из ИТМО чаще всего публикуется с соавторами не из ИТМО?» |
 
Правила:
 
- `dept_id` — всегда субъект, то есть подразделение, **чьих людей или публикации** возвращает вопрос. `partner_dept_id` — вторая сторона. В вопросе «Кто из X публиковался с авторами из Y» субъект X, партнёр Y. Для симметричных вопросов («есть ли общие публикации у X и Y») порядок не важен, субъектом считай первое названное.
- Ключ `dept_ids` в типе 3 больше не используется.
- В подтипе `3e` людей в `params` нет: `person_ids` отсутствует, `target` всегда `persons`, результат ранжируется по числу соавторов. Если `dept_id` не указан, субъект — весь ИТМО.
Ключи для типа 3:
 
- `target`: `persons` (соавторы или люди подразделения) или `publications` (совместные публикации).
- `metric`: `list`, `count` или `exists` («есть ли»).
- `coauthor_is_itmo: false`, если спрашивают про внешних соавторов; `true` для соавторов из ИТМО.
- Период: `year_from`/`year_to` или `last_n_years`.
- `rank_by` (только вместе с `order`): `distinct_coauthors` (число различных соавторов) или `joint_publications` (число совместных публикаций). Если не указан: для `3b` считается `joint_publications`, для `3e` — `distinct_coauthors`. Пиши ключ, только когда вопрос требует другого: например, «кто чаще всего публикуется с внешними» в `3e` означает `joint_publications`.
- «С кем у X наибольшее число публикаций»: `3b`, `target: "persons"`, `metric: "list"`, `order: "desc"`, `limit: 1`.
- Всё остальное — `none`: глобальные пары без якоря («у каких двух сотрудников самое большое число совместных публикаций»), внешние организации, средняя численность коллектива, цепочки соавторства, «ни разу не публиковался в соавторстве», тройки подразделений, ранжирование внешних авторов как субъектов.
Примеры `params`:
 
```json
{"target":"persons","dept_id":"<id Национального центра когнитивных разработок>","metric":"list","order":"desc","limit":1}
{"target":"persons","dept_id":"<id центра X>","partner_dept_id":"<id института ИИ>","metric":"list"}
```

### 5.5. Тип 5: цепочки (именованные шаблоны)

Тип 5 покрывает только три фиксированных паттерна. Всё остальное — `none` с пояснением в `note`.

| `pattern` | Смысл |
|---|---|
| `author_contributor` | Человек — автор публикации и контрибьютор репозитория, который эту публикацию реализует (`IMPLEMENTS`). |
| `author_not_contributor` | Человек — автор публикации, у которой есть реализующий репозиторий, но сам в нём не контрибьютор. |
| `author_with_repo` | Человек — автор публикации, у которой есть реализующий репозиторий с заданными свойствами. |

Ключи: `target: "persons"`, `pattern`, необязательные `dept_id` и `filters` (поля репозитория из раздела 5.2 для типа 4).

### 5.6. Типы 6–10: тема, подразделение, код, время

Типы 6–10 — варианты одного запроса «по теме». Они различаются необязательными частями, и один вопрос может сочетать несколько. Тогда в `params` записываются все части, а `type` — тип раздела, в котором стоит вопрос (тег `composite`).

| Ключ | Значение |
|---|---|
| `topic` | Тема как короткое именное словосочетание в именительном падеже. Убери служебные слова («кто занимается», «работы по»), оставь термины как в вопросе. Не переводи и не расшифровывай. |
| `target` | `persons` (кто), `publications` (какие публикации/работы/статьи), `repositories` («где есть код») |
| `metric` | `list` по умолчанию, `exists` для «есть ли». |
| `dept_id` | Для типа 8. |
| `year_from`, `year_to`, `last_n_years` | Для типа 10. |
| `require_code` | `true` для типа 9. |
| `link` | `mentions` (по умолчанию, если в вопросе «есть код», «есть ссылка на репозиторий», «сопровождаются кодом») или `implements` (если вопрос говорит «реализация», «IMPLEMENTS», «официальный»). Только при `require_code`. |
| `repo_filters` | Условия на репозиторий (лицензия, звёзды, язык) в формате `filters` из раздела 5.2. Только при `require_code`. |

## 6. `behavior`

- `answer` — обычный случай и все вопросы, которые обработает шаблон или запасной свободный Cypher.
- `clarify` — вопрос нельзя выполнить без уточнения (например, названо только имя без фамилии, где нужна однозначность).
- `refuse` — в схеме графа нет данных, чтобы ответить (например, история смены аффилиаций по годам). Тогда `type = none`, тег `no_data`.

Если у вопроса `type = none`, но данные в графе есть, `behavior = answer`.

## 7. Теги

Используй только эти значения: `case_form` (имя или подразделение стоит не в именительном падеже), `abbrev` (аббревиатура: ИИ, НЦКР), `two_entities`, `years`, `relative_period`, `negation`, `group_by`, `ranking`, `ambiguous_name` (человек назван только фамилией), `no_data`, `composite`, `check_value` (значение перечисления угадано), `needs_review`.

## 8. Типичные ошибки (проверь результат)

1. В строке не 11 полей. Это сдвигает JSON в соседнюю колонку.
2. В `params` стоит `null` вместо отсутствующего ключа.
3. Деталь вопроса потеряна: отрицание, «по отдельности», «в каждом», «с учётом иерархии», условие на поле. Если выразить нельзя — `none`.
4. Метрика не указана или не соответствует вопросу («кто» дает `list`, «сколько» — `count`).
5. «С 2022 года» записано как `year_from: 2021` или наоборот.
6. Все строки в одном сплите.
7. Заглушка заменена выдуманным id. Id подставит скрипт, ты пишешь `<id название>`.
8. Тег `no_data` ставится там, где данные в графе есть, а вопрос просто нельзя выразить шаблоном.

9. Не проходит валидатор. Готовый файл проверяется так: `python validate_questions.py test_questions.csv --docx вопросы.docx`. Все `ERROR` должны быть исправлены, `WARN` просмотрены.
